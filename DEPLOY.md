# Deploy Instructions — Tuscany Storage

Production hosting: **Render**. Domain points at Render web service. MongoDB is external (Atlas). Stripe is external (Stripe dashboard). Recurring billing runs as a Render Cron Job that calls back into the web app.

---

## TL;DR cost

| Component | Plan | Cost |
|---|---|---|
| Web service (Next.js) | Render **Starter** ($7) — always-on, no cold start | $7/mo |
| Recurring billing cron | Render **Cron Job** — pay per compute minute | ~$0.10–$0.50/mo |
| MongoDB | MongoDB Atlas M0 (free) or M10 ($57) | free → $57/mo |
| Stripe | pay-as-you-go (2.9% + $0.30 per charge) | usage-based |
| **Total fixed (demo)** | | **~$7.50/mo** |

> Render $7 Starter is **always-on** — only the Free tier sleeps. Don't downgrade to Free or the public reserve flow will cold-start.

When the facility grows past ~500 active leases or you want zero-pause peace of mind for the cron, bump web to **Standard ($25)**.

## First-time setup on Render

1. Create a Render account, click **New +** → **Blueprint**.
2. Connect this repo and point the blueprint at `render.yaml` (already in the root).
3. Render creates two services:
   - `tuscany-storage` (web, $7 Starter)
   - `tuscany-recurring-billing` (Cron Job, pay-per-minute)
4. Set the **env vars** below in the Dashboard for each service.

### Required env vars

| Var | Where | Value |
|---|---|---|
| `MONGODB_URI` | web | Atlas connection string |
| `NEXTAUTH_URL` | web | `https://tuscany-storage.onrender.com` (or custom domain) |
| `NEXTAUTH_SECRET` | web | `openssl rand -base64 32` |
| `STRIPE_SECRET_KEY` | web | from Stripe dashboard (`sk_live_...` or `sk_test_...`) |
| `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | web | from Stripe dashboard (`pk_live_...` or `pk_test_...`) |
| `CRON_SECRET` | both | autogenerated by Render — keep in sync between services |
| `APP_URL` | cron | the public URL of the web service, e.g. `https://tuscany-storage.onrender.com` |

> The `render.yaml` is configured so `CRON_SECRET` is generated by the web service and pulled in by the cron via `fromService` — you should not need to set it manually.

### First deploy checklist

- [ ] Push to `main`
- [ ] Render builds & deploys (~5-7 min for first build)
- [ ] Confirm `https://<your-app>.onrender.com/` loads the home page
- [ ] Confirm `https://<your-app>.onrender.com/admin` redirects to sign-in
- [ ] Sign in with the seeded admin (`admin@tuscanystorage.com` / `admin123`) and **change the password immediately**
- [ ] Confirm the cron job's "Last run" works (manual run from Render dashboard)

## Cron job — recurring billing

**Schedule:** `0 8 * * *` (every day at 08:00 UTC = 03:00 ET).

**What it does** (full lifecycle in `app/api/cron/recurring-billing/route.ts`):

1. Iterates every `Lease` with `status: 'active'`
2. Resolves the tenant + unit
3. Skips if: lease inactive, autopay paused, no payment method on file
4. Computes the next charge date: `billingDay + tenant.billingDateOffset`
5. If today ≥ charge date and no successful Payment exists yet for this period:
   - Creates a Stripe `PaymentIntent` off-session with the saved card
   - Records a `Payment` row (status `succeeded` / `failed`)
6. Returns a summary: `{ total, charged, failed, skipped }`

### Manual triggers

Local dry-run (lists what would charge, no Stripe calls):

```
npm run billing:preview
```

Local real run (against your dev DB + Stripe test key):

```
npm run billing:run
```

In production from your machine (one-shot):

```
curl -X POST https://<your-app>.onrender.com/api/cron/recurring-billing \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"dryRun": true}'
```

In production from the Render dashboard: open the Cron Job service and click **"Run Now"**.

### Body params (optional)

```jsonc
{
  "date": "2026-06-01",       // pretend today is this date (for testing)
  "dryRun": true,             // don't actually charge
  "tenantId": "abc123..."     // only process this tenant
}
```

## Initial data seeding

After the first deploy, you'll have an empty DB. To populate it for the **Tuscany** facility:

```
# 1. Connect to prod DB (set MONGODB_URI to the prod URI in your local shell)
export MONGODB_URI="mongodb+srv://..."

# 2. Bootstrap settings doc (idempotent — backfills missing keys without overwriting)
npm run seed:settings

# 3. Seed the catalog (163 units matching the live site)
npm run seed

# 4. Seed retail products (14 typical storage items: locks, boxes, tape, etc.)
npm run seed:products

# 5. Seed the move-in promo
npm run seed:promo

# 6. Import existing customer roster from CSV
npm run seed:customers -- "path/to/Customers.csv"

# 7. Sync unit statuses (in case anything got out of sync)
npm run sync:units -- --apply
```

> Do **not** run `npm run seed` after the facility goes live — it drops `units`, `tenants`, `leases`, `payments`, etc. Use `seed:customers`, `seed:products`, `seed:settings`, and `sync:units` for incremental updates (all idempotent).

### Onboarding a NEW storage company (multi-tenant SaaS)

Same scripts, no manual schema work:

```
# 1. Point at the new client's fresh DB
export MONGODB_URI="mongodb+srv://...new-client..."

# 2. Bootstrap (settings doc + products + promo)
npm run seed:settings
npm run seed:products
npm run seed:promo

# 3. Admin signs in and customizes via the dashboard:
#    /admin/settings/facility    → facility name, address, phone, email
#    /admin/settings/fees        → adjust late/NSF/auction amounts
#    /admin/settings/protection-plans → tweak protection tiers
#    /admin/units/canvas         → lay out their physical units
#    /admin/retail               → adjust product catalog & inventory

# 4. (Optional) import their existing customer roster
npm run seed:customers -- "their-customers.csv"
```

`seed:settings` is non-destructive: when we ship a new release that adds a new settings field, re-running the script backfills that field for existing tenants **without touching their customizations**.

## Recovery: cron didn't run / charges missed a day

Replay a specific day:

```
curl -X POST https://<your-app>.onrender.com/api/cron/recurring-billing \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"date": "2026-06-15"}'
```

The sweep is idempotent — if a `Payment` already exists with `status: succeeded` or `pending` for the same period+lease, it skips and won't double-charge.

## Custom domain

1. In Render, open the web service → **Settings** → **Custom Domain**
2. Add `tuscanystorage.com` (or whatever Jess wants)
3. Update DNS at the registrar: CNAME → `tuscany-storage.onrender.com`
4. Update `NEXTAUTH_URL` env var to the custom domain
5. Update `APP_URL` env var on the cron service to the custom domain

## Monitoring / health

Render dashboard surfaces:
- Web service logs (request log + console.log/error)
- Cron Job last-run history (timestamp + exit code + log)
- Bandwidth & CPU usage charts

For Stripe-side visibility:
- `https://dashboard.stripe.com/payments` shows every charge attempt
- Failed off-session charges raise `payment_intent.payment_failed` webhooks — wire one if/when Jess wants automatic email-the-tenant on failure (currently the `Payment` row has `status: 'failed'` + `failureReason` so admin sees it in the dashboard)

## When to upgrade

| Trigger | Action |
|---|---|
| > 500 active leases | Web → Render Standard ($25) |
| Cron run > 2 min consistently | Cron job → larger plan or split by floor |
| Reserve flow latency complaints | Add CDN / move to Render with a Premium plan |
| Want preview deploys per PR | Migrate to Vercel Pro ($20) — `vercel.json` cron config is trivial |
